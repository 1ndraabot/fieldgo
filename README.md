## Menjalankan
1. `cp .env.example .env` lalu isi `DATABASE_URL` (pooler Supabase, port 6543), `DIRECT_URL` (port 5432), dan `APP_URL`.
   Supabase dipakai **hanya sebagai host PostgreSQL** lewat Prisma. Auth dibuat sendiri (bukan Supabase Auth, bukan `supabase-js`/PostgREST).
2. `npm install`
3. `npx prisma migrate dev --name init` lalu `npm run db:seed` (6 lapangan + 4 akun dummy)
4. `npm run dev` â†’ http://localhost:3000

## Auth
- Daftar (`/daftar`) â†’ email verifikasi â†’ Masuk (`/masuk`). Sandi di-hash scrypt; sesi disimpan di tabel `sesi` (cookie `HttpOnly`, `SameSite=Lax`, 7 hari); token verifikasi 24 jam, sekali pakai.
- **Lupa kata sandi** (`/lupa-sandi` → tautan email → `/reset-sandi?token=...`): token reset berlaku **1 jam**, sekali pakai; setelah sandi berganti **semua sesi pengguna digugurkan**. Respons permintaan selalu sukses (tidak membocorkan email terdaftar).
- **Email**: `MAILER=gmail` (Gmail SMTP via nodemailer), `resend`, atau `konsol` (tautan dicetak di terminal). Bila `MAILER` kosong, urutan otomatis gmail → resend → konsol.
- Akun belum terverifikasi boleh masuk tetapi tidak boleh memesan (banner pengingat + `/pesan`).
- **Jadwal saya** (`/jadwal-saya`): hanya untuk penyewa yang masuk; menampilkan pesanan **Terkonfirmasi** dan **Menunggu pembayaran** milik akun di sesi (yang sudah selesai atau lewat batas bayar disembunyikan). Seed menambah 4 pesanan DUMMY untuk `penyewa@contoh.id` (satu berstatus Menunggu verifikasi untuk membuktikan penyaringan). Tombol "Bayar sekarang" menuju halaman Pembayaran di bawah.
- **Pembayaran** (`/pesanan/{kode}/bayar`): hanya untuk pemilik pesanan (milik orang lain = 404). Menampilkan stepper, batas bayar dengan hitung mundur, total tagihan, dan ringkasan pesanan. Tombol **Bayar sekarang** membuat invoice di payment gateway (Xendit Invoice API) di server — nominal dan item tidak pernah berasal dari klien — lalu mengarahkan ke halaman pembayaran Xendit. Status pesanan diperbarui otomatis dari callback (`x-callback-token` diverifikasi, nominal dicocokkan, notifikasi idempoten); halaman juga melakukan polling ringan selama menunggu. **Batalkan pesanan** langsung hanya selagi Menunggu pembayaran (slot dilepas). Pembayaran telat atau nominal tidak cocok **tidak** mengubah status otomatis: transaksi ditandai perlu tinjau untuk diputuskan admin. Tampilan berganti menurut status (terkonfirmasi, ditolak, dibatalkan, kedaluwarsa, selesai).
- **Gateway Xendit**: isi `XENDIT_SECRET_KEY` dan `XENDIT_CALLBACK_TOKEN` di environment (jangan pernah ke DB/klien), lalu daftarkan callback `https://<domain>/api/gateway/xendit` di dashboard Xendit (untuk lokal gunakan tunnel). `GATEWAY_PROVIDER=xendit` memakai Invoice API; sinkron manual dan refund memakai `provider_ref` (invoice id) yang disimpan per transaksi. `metode_aktif` di pengaturan dipetakan ke `payment_methods` Xendit: QRIS, GoPay, ShopeePay, kartu kredit, serta VA `BCA`/`BNI`/`BRI`/`MANDIRI`/`PERMATA` untuk transfer bank.
- **Mode simulasi gateway**: untuk pengembangan tanpa memanggil Xendit, `GATEWAY_PROVIDER="fake"` (hanya aktif di non-production) menggantikan Invoice API. Setelah menekan Bayar sekarang, halaman `/pesanan/{kode}/bayar/simulasi?order=...` menawarkan simulasi berhasil/gagal/kedaluwarsa; notifikasi dikirim ke `POST /api/gateway/fake` dan diproses lewat jalur webhook yang sama. Tabel `pembayaran` (bukti transfer manual) dipertahankan sebagai arsip dan tidak dipakai lagi oleh alur baru.
- **Storage bukti**: bila `SUPABASE_URL` dan `SUPABASE_SERVICE_ROLE_KEY` diisi, berkas ke bucket **privat** Supabase Storage (REST dari server); bila kosong (pengembangan), berkas ke folder `.data/` (dummy, di luar git). Di produksi tanpa konfigurasi, unggah ditolak. Buat bucket `bukti-pembayaran` (privat) di dashboard Supabase.
- Alur FR-PUB-05: tamu membuka `/pesan?...` â†’ diarahkan ke `/masuk?next=...` â†’ kembali ke slot yang sama. `/pesan` kini layar konfirmasi sungguhan.
- **Pemesanan** (`/pesan?lapangan=&tanggal=&mulai=&selesai=`, FR-ORD-01…05): layar konfirmasi menampilkan lapangan, tanggal, rincian harga per jam, total, dan batas bayar; tombol konfirmasi memanggil `POST /api/pesan`. Server memeriksa ulang slot di dalam satu transaksi (kunci `pg_advisory_xact_lock` per lapangan+tanggal → **anti double booking** meski indeks unik parsial belum ada), menghitung harga dari tarif (bukan dari klien), mengunci harga di `pesanan` + `slot_pesanan`, dan membuat kode `FGO-XXXXXX` (tanpa karakter ambigu). `batas_bayar_pada = min(dibuat + batas bayar dari Pengaturan (1–72 jam, default 24), jam mulai main)` (BR-07). Slot yang sudah dipegang orang lain atau diblokir admin → 409 dan UI menawarkan buka kalender lagi.
- **Riwayat** (`/riwayat`, FR-HIS-02…05): daftar seluruh pesanan milik sesi (terbaru dulu, filter status) dari basis data, bukan data contoh. Detail `/riwayat/{kode}` menampilkan rincian, bukti transfer (nama berkas), linimasa status asli dari `riwayat_status`, alasan penolakan, dan keputusan pembatalan. Pesanan `menunggu_pembayaran` yang lewat `batas_bayar_pada` langsung ditampilkan **Kedaluwarsa** tanpa menunggu worker (BR-09). `penggunaId` selalu dari sesi; pesanan orang lain = 404.
- **Pengajuan pembatalan** (`/riwayat/{kode}/batal`, FR-CAN-01…04): hanya untuk pesanan **Terkonfirmasi** dan paling lambat H-N pukul 23.59 WIB, dengan N = batas pembatalan dari Pengaturan (1–7 hari, default H-1); tombol/form disembunyikan setelah lewat dan server memeriksa ulang. `POST /api/pesanan/{kode}/batal-ajuan` menyimpan satu `pengajuan_pembatalan` per pesanan (UNIQUE), mengubah status → **Pengajuan pembatalan** dalam satu transaksi, dan **slot tetap terisi** sampai admin memutuskan (FR-CAN-03). Pengajuan kedua → 409; pengajuan yang ditolak tidak bisa diganti (FR-CAN-04).
- **Panel admin — lapangan, tarif, jam operasional** (`/admin/lapangan`, `/admin/tarif`, `/admin/jam-operasional`, FR-ADM-02…04): ketiga halaman membaca basis data dan menyimpan lewat API admin (`POST/PATCH /api/admin/lapangan[/{id}]`, `POST .../{id}/aktif`, `PUT .../{id}/tarif`, `PUT .../{id}/jam`, `POST/PATCH/DELETE /api/admin/jenis-olahraga[/{id}]`, `POST/PATCH/DELETE /api/admin/fasilitas[/{id}]`). Setiap route memeriksa sesi admin lebih dulu (401 tanpa sesi, 403 untuk penyewa) dan menjawab `{ok:false,kode,pesan}` dengan status 400 `VALIDASI`, 404 `TIDAK_DITEMUKAN`, 409 `KONFLIK`, 503 `MODE_DEMO`. Aturan bisnis ada di `lib/admin/lapangan/rules.ts` dan dipakai server sekaligus UI: harga > 0, rentang tidak tumpang tindih, dan **seluruh jam buka tiap tipe hari harus tertutup tarif**; jam operasional tepat 7 baris (hari tutup diperbolehkan), dan perubahan jam yang menyisakan jam tanpa tarif ditolak. Simpan tarif/jam bersifat **ganti-semua dalam satu transaksi**, sehingga pesanan lama tidak berubah karena harga sudah dikunci di `slot_pesanan.harga_per_jam` (BR-06). Lapangan **tidak dihapus fisik**: hanya dinonaktifkan (BR-17) — halaman publiknya menjadi 404, pesanan berjalan tetap diproses. Lapangan baru otomatis dibuatkan jam operasional standar 7 hari 06.00–24.00 sehingga admin tinggal mengisi tarif. Fasilitas memakai tabel `fasilitas` + `lapangan_fasilitas`; jenis olahraga atau fasilitas yang masih dipakai lapangan tidak bisa dihapus (409). Tanpa `DATABASE_URL` (mode DEMO) semua mutasi menjawab 503 `MODE_DEMO`.

- **Panel admin — pengaturan** (`/admin/pengaturan`, FR-ADM-11): `POST /api/admin/pengaturan` menyimpan rekening tujuan (hanya info refund manual), batas bayar 1–72 jam, batas pembatalan 1–7 hari, toggle `gateway_aktif`, dan `metode_aktif[]` (QRIS, VA bank, e-wallet). Nilai disimpan sebagai baris `pengaturan` (`kunci` + `nilai` jsonb, bentuk fieldgo). Kredensial gateway **tidak** pernah masuk basis data atau klien. Batas bayar dan pembatalan dibaca saat pesanan/pengajuan dibuat sehingga pesanan lama tetap memakai nilai yang sudah dikunci; mematikan gateway menyembunyikan tombol bayar (banner) dan `POST /api/pesanan/{kode}/bayar` menjawab 503 `GATEWAY_NONAKTIF`.
- **Panel admin — blacklist jadwal** (`/admin/blacklist`, FR-ADM-05, AC-15): `POST /api/admin/blacklist/cek` memeriksa bentrok, `POST /api/admin/blacklist` menyimpan (409 `KONFLIK` + daftar `bentrok` bila perlu `abaikanBentrok:true`), `DELETE /api/admin/blacklist/{id}` menghapus. Slot terblokir tampil **Terisi** dan ditolak `POST /api/pesan`. Sesuai **BR-14**, memblokir **tidak membatalkan** pesanan yang sudah berjalan: konfirmasi bentrok hanya acknowledgment, status pesanan terdampak tidak berubah dan tetap diproses.
- **Panel admin — pengguna** (`/admin/pengguna`, FR-ADM-10): `POST /api/admin/pengguna/{id}/aktif` dengan `{aktif:boolean}`. Hanya akun **penyewa** yang dapat diubah; admin tidak dapat menonaktifkan diri sendiri dan akun admin tidak dapat dinonaktifkan. Menonaktifkan tidak menghapus data: sesi berikutnya langsung gugur (401 karena `ambilPengguna` mengabaikan akun nonaktif), login menjawab 403 `AKUN_NONAKTIF`, dan pesanan berjalan tetap diproses. UI menyediakan pencarian, filter peran/status, dan konfirmasi sebelum mengubah.
- **Panel admin — pembayaran & pembatalan** (`/admin/pembayaran`, FR-ADM-06/07; `/admin/verifikasi` lama dialihkan ke sini): tiga tab — Pengecualian, Pengajuan batal, Refund — diisi dari basis data. `POST /api/admin/pembayaran/{kode}/tinjau` menerima (`terima`) hanya bila alasan `BAYAR_TERLAMBAT`/`STATUS_PESANAN_BERUBAH`; nominal tidak cocok atau permintaan tinjau provider **wajib** `refund`. Penerimaan memeriksa ulang bentrok slot di dalam transaksi (409 `SLOT_TERPAKAI` → UI langsung menawarkan refund penuh) lalu mengunci slot kembali. Refund gateway memanggil `GatewayProvider.refund`: sukses → refund `diproses` + transaksi `refund`; gagal → refund `gagal` dengan cara `manual` + 502 (`GATEWAY_GAGAL`/`GATEWAY_TIDAK_TERJANGKAU`) agar admin menyelesaikan transfer manual. Satu refund aktif per transaksi (409 `SUDAH_ADA_REFUND`); keputusan mengeluarkan pembayaran dari antrean pengecualian. `POST /api/admin/verifikasi/batal/{kode}` menyetujui (pesanan **Dibatalkan**, slot dilepas, refund gateway bila ada tagihan gateway — manual bila tidak; nominal default total pesanan) atau menolak (kembali **Terkonfirmasi**, catatan wajib ≥ 5 karakter yang tampil di detail pesanan penyewa). `POST /api/admin/refund/{kode}` membuat refund manual/gateway langsung, dan `POST /api/admin/refund/{kode}/selesaikan` menandai transfer manual selesai. `POST /api/admin/pembayaran/{kode}/sinkron` menarik status terakhir dari gateway lalu memprosesnya lewat jalur webhook yang sama (idempoten); provider fake menjawab 409 `BELUM_ADA_INFO`. Semua route memakai guard admin yang sama (`{ok:false,kode,pesan}`; 400 `VALIDASI`, 404 `TIDAK_DITEMUKAN`, 409 status, 502 gateway, 503 `MODE_DEMO`).
- **Panel admin — pesanan** (`/admin/pesanan`, FR-ADM-08): daftar seluruh pesanan dari basis data dengan pencarian (kode/penyewa/lapangan) dan filter status di server, 50 baris per halaman. Detail `/admin/pesanan/{kode}` menampilkan identitas penyewa, slot aktif, seluruh percobaan `pembayaran_gateway` (status, metode, waktu, alasan tinjau), refund, pengajuan pembatalan beserta putusannya, dan linimasa `riwayat_status`. Tombol **Sinkronkan dengan gateway** memakai endpoint yang sama dengan tab Pengecualian.

## Tes
`npm test`: 144 tes logika murni dengan `node:test`, tanpa dependensi (Node ≥ 22.6): format, status slot, pilihan jam, aturan validasi, hash sandi, rate limiter, cookie, service auth, pemesanan, riwayat/pembatalan, aturan gateway pembayaran (Xendit), aturan admin lapangan/tarif/jam, pengaturan, blacklist, pengguna, pengecualian pembayaran/refund/pembatalan, dan handler HTTP. `npx tsc --noEmit` bersih.

Migrasi SQL di `prisma/migrations/` diterapkan manual ke database fieldgo (tidak ada `_prisma_migrations`); jangan menjalankan `prisma migrate dev`.
